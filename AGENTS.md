# AGENTS.md

Project: learning/demo repo of agentic design patterns using LangChain + AWS Bedrock. See `CLAUDE.md` for the deep-dive guide; `README.md` is kept in sync with current module names.

## Commands

```bash
uv sync                # install deps (use this before anything; never pip install)
uv run pytest          # run all tests (10 tests; configured in pytest.ini, asyncio auto)
uv run pytest tests/test_spec_extractor.py -q   # run one test file
uv run app             # entry point; validates AWS creds then prints example help
uv run python -m src.examples help             # list examples
uv run python -m src.examples prompt_chaining  # run an example (needs live AWS creds)
uv run python -m src.examples routing          # run the routing example
uv run python -m src.examples parallelization  # run the parallelization example
uv run python -m src.examples reflection       # run the reflection example
uv run python -m src.examples tools            # run the tool use example
uv run python -m src.examples planning         # run the planning example
uv run python -m src.examples multiagent       # run the multi-agent example
uv run python -m src.examples state            # run the state management example
uv run python -m src.examples goal_monitoring  # run the goal setting and monitoring example
uv run python -m src.examples exception_handling  # run the exception handling example
uv run python -m src.examples hitl             # run the human-in-the-loop example
uv run python -m src.examples rag              # run the retrieval-augmented generation example
uv run python -m src.examples a2a              # run the agent-to-agent (A2A) example
uv run python -m src.examples resource_optimization  # run the resource-aware optimization example
```

No linter, formatter, or typecheck config exists. Do not invent one; just run `pytest`.

## Architecture

- Example registry + CLI helpers live in `src/app/cli.py` (EXAMPLES dict, `print_help`, `CMD_*` constants) — NOT `src/examples/cli.py`.
- `src/examples/__main__.py` is the example CLI dispatcher using dictionary dispatch; its `main()` calls `validate_aws_credentials()` before running **any** example. Add a new helper function and register it in the `COMMANDS` dict.
- `src/app/config.py` calls `load_dotenv()` at import time; env vars are read as module constants. `src/app/bedrock.py` builds the `ChatBedrock` instance at import time and calls `validate_aws_credentials()` at module scope.
- `src/app/examples.py` is dead legacy code (pre-dates the `src/examples/` package); don't extend it.
- Several example modules were renamed (git mv): `routing/cordinator_agent.py` -> `routing/request_router.py`, `reflection/reflection.py` -> `reflection/draft_refiner.py`, `tools/tool_use.py` -> `tools/tool_calling_agent.py`. Use the new names; CLAUDE.md/README may still show the old ones.
- Every example's entry point is `handle_requests()`, exported from its package `__init__.py` and wired into `src/examples/__main__.py` via a `_run_<name>()` helper + `COMMANDS` dict entry, with a `CMD_<NAME>` constant and description in `src/app/cli.py` `EXAMPLES`.
- `src/examples/routing/request_router.py` demonstrates the Routing pattern: an LLM classifies each request into one `HANDLERS` key (`booker`, `info`) or `unclear`, then a `RunnableBranch` dispatches the untouched request to that plain-Python handler. `build_router()` composes `{"category": classifier_chain, "request": passthrough}` into the branch; `HANDLERS` is the single source of truth (branch conditions are generated from it). The model decides once, then is out of the loop.
- `src/examples/parallelization/text_analysis.py` demonstrates the Parallelization pattern: three independent sub-chains (summary, sentiment, keywords) fanned out via `RunnableParallel` and merged into one report — not a sequential `|` chain like `prompt_chaining`.
- `src/examples/reflection/draft_refiner.py` demonstrates the Reflection pattern: a generate -> reflect -> refine loop over three plain LCEL chains (`build_generate_chain`, `build_reflect_chain`, `build_refine_chain`), each built fresh per call. The loop runs in `run_reflection_loop`, capped at `MAX_ITERATIONS` and exiting early on an exact-match `APPROVAL_TOKEN` from the reflector.
- `src/examples/tools/tool_calling_agent.py` demonstrates the Tool Use / function-calling pattern — NOT a fixed LCEL pipeline. Three `@tool` functions (`calculator`, `get_weather`, `word_count`) are bound via `llm.bind_tools(TOOLS)`; `run_agent()` hand-rolls the observe -> decide -> act loop over a growing `list[BaseMessage]`, appending a `ToolMessage` (keyed by `tool_call_id`) per requested call and re-invoking until the model answers without tool calls or `MAX_STEPS` (5) is hit. Registered as `CMD_TOOLS` / `_run_tools`. Tool errors and unknown tool names are returned as strings, never raised.
- `src/examples/planning/task_planner.py` demonstrates the Planning (plan-and-execute) pattern — also not a fixed pipeline. `run_planner()` runs three stages per goal: `build_planner_chain()` (`prompt | llm | StrOutputParser() | _parse_plan`) decomposes the goal into an ordered `list[str]` capped at `MAX_STEPS` (6) — `_parse_plan()` normalises the model's inconsistent list formatting and truncates rather than raising; a deterministic loop calls `build_executor_chain()` once per step (each call sees the goal, full plan text, and `_format_completed()` prior results); `build_synthesis_chain()` merges the step results into the final answer. The whole plan is committed to before any step runs. Registered as `CMD_PLANNING` / `_run_planning`.
- `src/examples/multiagent/research_team.py` demonstrates the Multi-Agent pattern — also not a fixed pipeline. `SPECIALISTS` maps each name (`researcher`, `analyst`, `writer`) to `(one-line role summary, full system prompt)` in one dict so the supervisor's menu and the agents can't drift. `run_team()` loops up to `MAX_TURNS` (6): `build_supervisor_chain()` reads the goal + `_format_transcript()` and returns one specialist name or `DONE_TOKEN` (`"DONE"`); `_choose_next()` reduces the raw reply to its first word and maps it to a specialist, `DONE_TOKEN`, or `None` (unrecognised -> stop + log). The chosen specialist's chain (built once per name, reused) runs and appends its `(name, message)` pair to the shared transcript. `build_editor_chain()` then always runs one deterministic final pass over the whole transcript. Routing between teammates is decided at runtime from the evolving transcript. Registered as `CMD_MULTIAGENT` / `_run_multiagent`.
- `src/examples/state_layers/state/state_manager.py` demonstrates the State Management pattern — a fixed step sequence, unlike `tools`/`planning`; the interesting part is memory retention, not control flow. One `ConversationState` dataclass (`facts: dict`, `summary: str`, `recent: list[tuple[str, str]]`) is created once in `run_conversation()` and mutated in place by every helper. Per turn: RETRIEVE (`_format_facts`/`_format_recent` flatten state into prompt vars), RESPOND (`build_respond_chain()`), RECORD (append `("user", msg)` and `("assistant", reply)` to `recent`), UPDATE — `build_fact_chain()` emits `key: value` lines or `NO_FACTS_TOKEN` (`"NONE"`) which `_merge_facts()` parses leniently (skips malformed lines, overwrites on repeat) into `facts`; then `_compress_recent()` `while`-pops `recent` down to `2 * MAX_RECENT_TURNS` (3) entries, folding each evicted turn into `summary` via `build_summary_chain()`. Chains are built once and reused; all continuity lives in the state object. Registered as `CMD_STATE` / `_run_state`.
- `src/examples/reliability_layers/exception_handling/resilient_agent.py` demonstrates the Exception Handling / error-recovery pattern — the same hand-rolled tool-calling loop as `tools`, hardened. Tools raise `TransientError` / `PermanentError` (base `ToolError`); a catch-all in `_attempt_with_retries()` re-wraps anything else as permanent so the loop can't crash. `call_tool_with_recovery()` (never raises) runs the ladder: retry only transient failures up to `MAX_RETRIES` (3) with exponential backoff (`BACKOFF_BASE_SECONDS` (0.5) `* 2 ** (attempt-1)`), then consult `FALLBACKS` (`fetch_stock_price` -> `fetch_stock_price_backup`, the latter kept out of the model-visible `PRIMARY_TOOLS`) with its own retry budget, then `_degraded()` returns a `TOOL_UNAVAILABLE:` (`UNAVAILABLE_PREFIX`) note the system prompt tells the model to work around. Flakiness is scripted via the module-level `_price_calls` counter (persists across `SAMPLE_QUERIES` on purpose), so runs are deterministic. `run_agent()` mirrors the `tools` loop but routes calls through `call_tool_with_recovery()`. Registered as `CMD_EXCEPTION_HANDLING` / `_run_exception_handling`; first module under `reliability_layers/`.
- `src/examples/reliability_layers/hitl/approval_agent.py` demonstrates the Human-in-the-Loop pattern — the same hand-rolled tool-calling loop as `tools`, but a fixed policy set `SENSITIVE_TOOLS` (`book_flight`, `send_email`, `cancel_booking`) is intercepted before it runs. `run_agent(query, reviewer)` routes every call through `_dispatch_call()` (always returns a string): `request_human_input` (a real bound tool) → `reviewer.decide()` → `HUMAN_RESPONSE:`; non-sensitive tool → run now; sensitive tool → `reviewer.decide()` returning a `ReviewDecision` with `action` `APPROVE` (run as-is) / `EDIT` (run with `edited_args`, prefix `HUMAN_EDITED:`) / `REJECT` (don't run, prefix `HUMAN_REJECTED:` — system prompt says don't retry). `Reviewer` is a one-method protocol; `ScriptedReviewer` replays canned decisions keyed by tool name (FIFO, safe default = deny) so the demo runs unattended, `ConsoleReviewer` blocks on `input()` and is not wired into `handle_requests()`. `SAMPLE_SESSIONS` pairs each request with its reviewer script, one per branch (approve / edit / reject / clarify). Registered as `CMD_HITL` / `_run_hitl`; second module under `reliability_layers/`.
- `src/examples/state_layers/goal_monitoring/goal_tracker.py` demonstrates the Goal Setting and Monitoring pattern — fixed control flow, objective stop condition. `run_goal_loop()` first calls `build_criteria_chain()` once to decompose the goal into a checklist; `_parse_criteria()` strips list markers and truncates to `MAX_CRITERIA` (6). Then it loops up to `MAX_ITERATIONS` (4): `build_worker_chain()` re-produces the whole draft from `(goal, criteria, previous draft, feedback)`; `build_monitor_chain()` must emit one `<n>. MET` / `<n>. UNMET - reason` line per criterion; `_parse_progress()` matches those positionally to criteria (missing/unparseable line ⇒ UNMET, the safe default) yielding `list[tuple[str, bool, str]]`. Loop exits when `met_count == len(criteria)`, else `_format_feedback()` passes the unmet lines back to the worker; the `for/else` logs the give-up path. Loop state is just `draft` + `progress`. Registered as `CMD_GOAL_MONITORING` / `_run_goal_monitoring`.
- `src/examples/reliability_layers/rag/rag_pipeline.py` demonstrates the Retrieval-Augmented Generation pattern — a fixed three-stage pipeline, no model-driven control flow. `run_rag()`: RETRIEVE — `retrieve()` scores every `Document` in `KNOWLEDGE_BASE` by lexical term overlap (`_score()`, a deterministic stand-in for embeddings/vector search) and keeps the top `MAX_CONTEXT_DOCS` (3) above `MIN_RETRIEVAL_SCORE` (1); zero hits short-circuits to a refusal with no LLM call. AUGMENT — `_format_sources()` renders the kept docs as a numbered `[n]` block. GENERATE — `build_answer_chain()` answers *only* from that block, cites `[n]` per claim, or emits exactly `INSUFFICIENT_CONTEXT_TOKEN` (checked by exact match) when the sources don't cover the question; `_check_citations()` then flags (not hard-fails) any cited `[n]` outside the retrieved range. Registered as `CMD_RAG` / `_run_rag`; first module under `reliability_layers/` to have no tool loop at all.
- `src/examples/production_patterns/a2a/a2a_orchestrator.py` demonstrates the Agent-to-Agent (A2A) pattern — capabilities live behind independent services, not local functions. Each service is a `RemoteAgentService` wrapping an `AgentCard` (name/description/skills) + a `Handler`; `AgentRegistry` stands in for discovery (`register`/`discover`/`connect`). `run_orchestrator()`: `build_dispatch_chain()` picks one card's name or exactly `NO_AGENT_TOKEN` (`"NONE"`) from the discovered roster; `build_request_chain()` crafts the `Message` sent over `RemoteConnection.send()` (a direct call standing in for an HTTP POST). The remote side drives an explicit `Task` lifecycle in `execute()` — `SUBMITTED` → `WORKING` → `COMPLETED` / `INPUT_REQUIRED` / `FAILED`, never raising. On `INPUT_REQUIRED`, `build_followup_chain()` answers the agent's question and re-sends against the same `task_id`, up to `MAX_ROUNDS` (3); on `COMPLETED`, `build_synthesis_chain()` relays the result. Two demo agents (`_fx_handler`, `_weather_handler`) each ground an LLM phrasing call in a hard-coded table. First module under `production_patterns/`; registered as `CMD_A2A` / `_run_a2a`.
- `src/examples/production_patterns/resource_optimization/resource_optimizer.py` demonstrates the Resource-Aware Optimization pattern — the agent spends a finite `Budget` (`total`/`spent`/`remaining` property/`spend()`) across a fixed list of report sections (`SUBTASKS`, required sections listed first; `run_report()` re-sorts on `not s.required` so required work is always priced before optional). `select_tier(costs, remaining, required)` returns the richest paid tier (`PREMIUM` full LLM call → `STANDARD` terse LLM call → `ECONOMY` a cached fact from `_ECONOMY_CACHE`, no LLM call) that fits what's left, else `PLACEHOLDER` (free static note; required sections only, so one is never silently dropped) or `SKIP` (optional sections only). After all sections run, an LLM `build_synthesis_chain()` pass merges them if `budget.remaining >= SYNTHESIS_COST`, else they're concatenated as-is (`_format_sections()`) with no further spend. `SAMPLE_RUNS` holds the company/task fixed and varies only the budget (70 / 10 / 3 units) to walk the whole ladder. Second module under `production_patterns/`; registered as `CMD_RESOURCE_OPTIMIZATION` / `_run_resource_optimization`.
- Logging uses lazy % formatting (not f-strings) for efficiency; configured globally in `pyproject.toml` to disable `import-outside-toplevel` pylint warnings (lazy imports are intentional for startup speed).

## Gotchas

- Tests already exist in `tests/` (`test_cli.py`, `test_config.py`, `test_spec_extractor.py`) and pass. CLAUDE.md's "Currently no test suite" is outdated.
- Importing any module that touches `src.app.bedrock` (e.g. `spec_extractor.py`) requires AWS credentials at import time. In tests, mock the chains / LLM and pass mocks to `run_and_validate`; never import examples just to inspect data.
- The examples CLI validates credentials upfront, so examples cannot run offline; tests must not invoke the CLI's `main()`.
- Python is pinned to 3.14 (`.python-version`); `pyproject.toml` requires >=3.12.

## Adding an example

1. `src/examples/<name>/<module>.py` with a `run_*()`/entry function
2. `src/examples/<name>/__init__.py` exporting it
3. Register description in `src/app/cli.py` `EXAMPLES` dict and add `CMD_*` constant
4. Add helper function and register in `COMMANDS` dict in `src/examples/__main__.py`
5. Verify: `uv run pytest`
